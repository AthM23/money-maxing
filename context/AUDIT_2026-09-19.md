## Defects fixed

| Finding | Change and evidence |
|---|---|
| A declined proposal could later be approved; a stranger could decline it | Explicit terminal decline check and approval-matrix identity/type checks, including rejection. Regression probes cover both. |
| Balance/evidence checks and posting were separate operations | Proposal and approval gates now acquire the SQLite writer transaction before reading and hold it through posting. |
| Unapplied or partly applied cash could be counted incorrectly and reused | Bank consumption is the posted cash movement, including money held as customer credit; ledger and audit reads agree. |
| Replay could return an existing live posting | Replay has a separate decision result and does not consume live bank availability. |
| Superseded source evidence remained usable | Live searches return current versions, the kernel rejects superseded traces, dependent facts lose active status, workpapers become stale, and affected intents hold for review. Posted books are preserved. |
| Unauthorized/retried answers poisoned the next Slack reply | Authorize and deduplicate before writing evidence; answer, trace, fact and resumed proposal share a transaction. |
| Standing answers had no date input; February expiry could become February 31 | Explicit expiry required for standing answers; Slack accepts expiry and rate; real month-end and calendar-date validation. |
| Fact authority ceiling could be mistaken for the amount the fact explains | Kernel re-computes the cited rate or fixed amount against invoice totals. A 10% fact cannot authorize an arbitrary larger adjustment. |
| Old learning generalized to any matching customer | Generated policies carry customer scope; leave-one-out respects that scope and the minimum evidence count. Legacy generated rules without scope are held by `J_SCOPE`. |
| Arbitrary invoice selection on ambiguous receipts | No FIFO guess when multiple candidates are plausible. Only complete explicit references or one unique exact subset qualify; bounded-search exhaustion leaves the case unresolved. |
| Same vendor and amount blocked a different month's AP bill | Duplicate identity now checks obligation or normalized invoice number; historical audit excludes bills paid later. |
| Skeleton bypassed earned autonomy | Skeleton and worker now use the earned setting consistently. |

| Bank file could partly ingest despite malformed timestamps | File parser rejects bad dates/timestamps, duplicate IDs, unsafe cent amounts and unclosed CSV quotes before ingestion. |
| Console exposed an unauthenticated financial read API on all interfaces | Binds to loopback. Stale workpapers have a visible review notice. |
| Benchmark could mix results, mis-score schema validity, crash on malformed JSON and select thresholds on test labels | Dependency-free strict scoring, protocol fingerprints, incompatible-merge rejection, unknown cost reporting, calibration-only threshold selection. ## New remittance scene

`pnpm demo:remittance` uses an isolated in-memory Northwind fixture, with no external calls.
An email dated July 16 contains fourteen per-invoice allocations for a July 18 ACH reference. The receipt is
$13,505 against $14,000 of invoices. The first invoice, `INV-3001`, is explicitly $495 short.

The router preserves the allocations, applies the cash, leaves that invoice's $495 open and hands the remainder
to investigation. The kernel independently parses the cited source and checks payer, reference, date, total and
every allocation. Moving the same shortfall to another invoice fails `E_REMIT`, even though the total still balances.

Supported email block:

```text
BEGIN REMITTANCE
Reference: NW-ACH-0718-0001
Date: 2026-07-18
Amount: 13505.00
invoice,amount
INV-3001,505.00
...remaining real invoice rows...
END REMITTANCE
```

The ellipsis above is documentation, not valid input; the runnable fixture generates all fourteen rows.
The Gmail connector currently reads message bodies, not XLSX attachments. Reference/date/amount and a resolved
payer are required. This is a narrow demonstrator, not general remittance extraction or a fine-tune benchmark.
